# VideoSpy 双层 RSI：Task 程序与 Meta 进化器

日期：2026-10-08。状态：基于当前源码的设计稿，尚未实现或验证。

完整循环、数据流、权限、版本更新与首版验收见 [双层循环实现规格](videospy_dual_layer_rsi_workflow.md)。实现细节以该规格为准。

## 1. 两层定义与候选代码的归属

Task 层是部署时回答视频问题的程序，记为 T；Meta 层是离线改进这个程序的进化器，记为 M。两层都固定模型权重，通过程序、配置和策略文档改变行为。

- Task 候选 T'：由当前 Meta 进化器 M 依据一批任务经验生成，修改任务执行程序。
- Meta 候选 M'：由固定外层更新器 G 依据多次 Task 进化经验生成，修改进化器本身。
- 固定验证器 V_T、V_M 分别筛选两类候选。G、验证器、计量器、数据权限和硬预算不进入第一版进化范围。

Task 层并不是另一个必须存在的代码生成 Agent。第一版由 M 中的 proposer 生成 T'，G 生成 M'，避免两个角色重复修改同一对象，也避免无限增加更高层更新器。

版本关系为：`T_{r+1} = V_T(T_r, M_s.propose_task(...))`。积累多个内层轮次后，生成并验证 `M_{s+1} = V_M(M_s, G.propose_meta(...))`。每次选择都允许保留原版本。

Task 按任务批次更新；Meta 按若干次候选生成与验证记录更新。被拒绝的候选和无更新轮次同样是 Meta 的经验。不同更新频率由反馈积累速度决定，不意味着 Task 逐题修改代码。

## 2. 当前代码已经提供什么

| 当前入口 | 可复用能力 | 尚缺能力 |
|---|---|---|
| `videospy/agent.py` | 工具决策循环、工具权限、重复请求拦截、独立最终回答 | 可插拔执行策略、代码候选装载与完整执行筛选 |
| `videospy/tools/*.py` | 三个多粒度工具、内部视觉模型调用、采样覆盖说明 | 可版本化的采样与表达策略、程序候选评测 |
| `videospy/core/trajectory.py` | 完整主消息、工具观察和 diagnostics | 结构化视觉观测元数据、完整调用与候选关联 |
| `videospy/model.py`、`metrics.py` | 模型调用记录、每题 token 汇总、调用时间与重试信息 | 全阶段成本归因、所有尝试的统一持久化、离线预算闭环 |
| `evolving/reflector/runner.py` | 逐题评估、按任务分组、检查点、Skill/Memory 调度 | 代码级诊断、主动调查、Task 与 Meta 程序 proposer |
| `evolving/optimizer/skill_optimizer.py` | 有来源的 Task/Domain 策略文档生成与审核 | 修改后程序的行为验证 |
| `evolving/storage/memory_store.py`、`evolved_config.py` | Skill/Memory/参数快照存取与推理注入 | Task/Meta 源码快照、候选档案、双层父子版本关系 |

以实际源码为准：当前反思评分为 0–5，分组按分数层级均衡取样；`bad_ratio` 已忽略，不应沿用 README 中旧的 z-score/Good-Bad 分组作为当前初始实现。

当前 `EvolutionPipeline` 是已有轨迹上的文档进化，不是程序 RSI。`hyperparameters` 有存取和白名单，但当前 pipeline 继承初始值，未实现参数搜索。SQLite 加载机制也不会装载任意候选源码。

## 3. Task 层可进化对象

### 3.1 视觉证据获取

| 对象及当前实现 | 第一版允许进化的行为 | 示例与约束 |
|---|---|---|
| `overview.py`：默认全视频均匀 64 帧，短边 256，2×4 拼图 | 全局帧分配、分辨率、拼图布局、问题相关观察提示 | 保持全局覆盖，减少近重复画面，保留采样时间；不能把未抽样时刻表述为已检查 |
| `clip_skim.py`：指定区间均匀最多 16 帧，短边 256 | 分段采样、粗到细的内部细化、局部帧预算与表达 | 可先粗扫再补看局部；新增内部模型调用都须计量，不能以一次公开调用掩盖无限工作 |
| `frame_inspect.py`：最多 4 个指定时刻、最近帧、不缩放 | 同次比较的组织、任务相关局部放大、分辨率与返回提示 | 第一版只使用请求时刻对应的帧；裁剪需保留原帧与位置，不悄悄读取其他时刻 |
| `tools/inspection.py` 与字幕选择 | 事实、解释、未知项的表达；允许范围内的字幕上下文策略 | 保留实际来源和不确定性；不能从任务题干或标签制造观察 |

三个工具继续使用现有 reader。MedVidBench 的 `ImageSequenceReader` 只有现有帧序列；EgoLife reader 受当前问题时间限制。候选不能绕过 reader 打开底层数据扩大权限。首版不增加原生视频模型接口、音频处理或新模型，避免改变比较条件。

### 3.2 任务执行与证据使用

| 对象 | 允许进化 | 初始接入建议 |
|---|---|---|
| 工具选择策略 | 首个工具、下一步证据目标、区间细化、冲突处理 | 抽出 `runtime_policy.py`；先以当前决策行为作为默认实现 |
| 工具说明和策略提示 | 描述真实能力、选择条件、任务条件分支 | 固定名称和必需参数，说明必须与执行一致；保留固定的答案与证据约束 |
| 证据状态与上下文 | 事实去重、支持关系、未知项、时间关联、模型输入压缩 | 抽出 `evidence_policy.py`；原始轨迹始终完整落盘，仅改变模型看到的工作上下文 |
| 继续/停止策略 | 是否需要新证据、选择哪种观察、何时进入最终回答 | 不超过固定硬上限，不绕过无字幕/无视觉证据的强制要求 |
| 执行参数 | 抽帧数、字幕窗口、单次时间点数量、软步数预算 | 参数值必须在外部固定范围内；现有白名单需与新配置契约同步 |
| Task/Domain Skill | 任务策略、触发条件、工具使用经验 | 随代码一起版本化和验证；工具行为改变后检查旧 Skill 兼容性 |

初始版本建议保留当前固定 SYSTEM_PROMPT 骨架，只开放策略附加区和工具内部提示。以后研究修改主提示时，应另设明确白名单，避免同时改变答案协议和证据政策。

已有工具说明已经建议已知时间直接局部定位，因此不能把这条建议本身当作新增改进。必须根据真实轨迹判断是执行偏离、工具限制还是观察表达问题。

任务类别应使用部署时可获得的类别，或固定分类器；不得借助测试标签决定策略。如果 benchmark 类别是额外提供的元数据，基线和候选必须获得相同信息。

### 3.3 Memory 的处理

事实 Memory 是任务资产，不是 Meta 的进化经验。第一版主程序实验建议关闭 Memory，或为父版本和候选使用相同冻结快照，避免将新增事实记忆的收益归为程序进化。启用时仍执行当前来源和时间过滤。

Task Skill 与 Domain Skill 都指导任务执行，均归 Task 层。Domain Skill 不等于 Meta 层。

## 4. 固定边界与接入方式

固定：模型配置、三个公开工具名称和必需参数、合法 reader、数据访问权限、标准答案访问范围、最终答案协议、评价器、成本计量、硬预算、候选接受准则。

不向候选开放整个 `agent.py` 或 `model.py`。将可进化策略抽为插件/函数，保留固定 Agent 包装器负责工具权限、重复请求保护、异常记录和最终输出。工具内核可修改，但由固定包装器记录实际采样信息与全部模型调用。

当前 `core/evidence.py` 依赖 `frame_inspect` 返回字符串前缀解析时间。首版保留兼容前缀；更稳妥的前置改造是增加固定结构化 observation 元数据，再开放自然语言表达。不能先任意修改工具输出，导致旧引用、Memory 或评估逻辑失效。

当前 Agent 只把 `model_calls[0]` 附在工具消息中；如果工具增加多次内部调用或发生重试，现有单条字段不足。需在固定记录器中保存完整调用列表，兼容原字段，并记录阶段、工具、attempt、usage、异常、elapsed、Task/Meta/candidate ID。失败调用缺失 usage 时记为未知；不得当零成本用于宣称节省。

`compact` 调用日志会省略图片 base64。因此原有轨迹不能直接用于复核图像细节。额外保存帧索引、时间映射、尺寸、拼图/裁剪变换、来源标识和哈希；按同一合法 reader 重建，必要时保留图像引用。输入字符数不能代替 token。

## 5. 初始 Meta 进化器 M0 与 Task 初始流程

M0 是人工固定的起始进化器，不应被描述为当前已有实现。复用现有轨迹读取、评估和分组能力，新增诊断、调查与代码提案阶段，不必原样启动依赖 Memory embedding 的整条旧 pipeline。

1. **初始化 T0。** 冻结基础版源码、配置、模型、Skill/Memory 状态、reader 和数据划分，记录所有哈希。先建立独立选择集上的父版本成绩。
2. **执行诊断批次。** 使用 T_r 完整运行一批问题，保留成功、失败、正确但昂贵、未完成和重复调用记录。任务批次固定版本，处理中不改程序。
3. **评估与案例选择。** 复用当前 0–5 评估和任务分组；兼顾错误/证据不足、正确但昂贵、正确且高效的对照。选择依据覆盖和信息价值，不只选最低分。反思分数是诊断信号，不替代固定 benchmark 正确性指标。
4. **生成诊断报告。** 每个问题族记录可见现象、涉及代码、竞争性解释、支持与反例、成本分布和未确定项。初始可使用采样覆盖、细节可见性、观察表达、证据使用、搜索策略五类标签，但允许多原因或未知。
5. **按需主动调查。** 只有额外观察能区分原因时才调查。通过合法 reader 定向补看；可在同一决策前缀上对比原动作、新采样动作和无新证据的重新推理。调查调用和后续续跑独立记录，不能作为候选部署效果。
6. **生成 1–2 个 Task 候选。** 提交实际补丁、配置差异、可选 Skill 更新、来源、假设、影响范围、反例和检查计划。优先一个主要机制，可有必要依赖改动，也允许无候选。
7. **分阶段验证。** 固定接口/权限与运行检查 → 诊断案例和反例执行 → 独立 Task 选择集完整 QA。局部成功才进入后阶段。候选改变后重新执行，不能把父版本轨迹作为候选成绩。
8. **选择与归档。** 按预先固定的质量—成本规则接受或拒绝，记录所有候选、异常和花费。接受后产生不可变 T_{r+1}；拒绝则保留 T_r。下一批重新收集当前版本经验。

M0 不默认奖励增加帧数，也不默认奖励更短答案。成本按主决策、三个工具内部调用、最终回答和新增辅助调用的完整 QA 累计；离线反思、调查、代码生成和评测单独累计。

Task 接受规则可沿用已有 RSI 设计：质量有可靠改善且成本增长不超固定阈值，或成本下降达到固定阈值且质量不低于预先声明下界。阈值、噪声处理及累计退化限制在搜索前固定。

## 6. Meta 层可进化对象

Meta 修改的是 M 如何完成第 5 节流程，而不是另一个回答视频题的 Agent。

| Meta 对象 | 可生成的代码/策略修改 | 预期行为变化 |
|---|---|---|
| 案例选择与分组器 | 按失败现象、成本、成功对照和历史覆盖选案例 | 减少反复分析同类问题，为诊断补足反例 |
| 诊断器 | 诊断提示、竞争解释生成、源码关联和调查触发 | 区分采样缺失、观察表达和下游推理问题 |
| 主动调查规划器 | 调查动作、同前缀比较、调查停止与预算分配 | 用较少额外运行排除错误解释 |
| Task proposer | 源码/证据组装、提案模板、修改范围、父候选选择 | 产出更可执行、有依据、可泛化的 Task 补丁 |
| 候选组合与局部修复 | 候选多样性、失败后的修复或放弃、已验证修改的组合 | 减少无效搜索和重复失败，组合仍作为新候选验证 |
| 预检与预算调度 | 在固定必检之外增加局部检查、决定哪些候选进入昂贵验证 | 提高每单位离线成本产生的有效候选数量 |
| 进化经验检索 | 历史尝试的摘要、索引、按机制检索 | 避免同一假设反复失败，保留适用条件 |

Meta 可修改诊断方法，不能修改 benchmark judge、固定反思评价口径以美化成绩，或修改最终接受阈值。它可决定放弃候选、增加预检，但所有拟接受候选仍必须完成外部强制验证。

首版只开放诊断器和 Task proposer，包括相关提示与输入组装代码。其余先固定。完成可信对照后再开放案例选择、主动调查及预算调度；自由度过大会让外层验证成本迅速上升。

## 7. M 生成 Task 候选所需输入

| 信息包 | 必需内容 | 作用 |
|---|---|---|
| 当前 Task 快照 | T ID、源码及依赖、配置、Skill/Memory、接口、哈希 | 修改真实父版本，避免凭空生成不兼容代码 |
| 诊断批次执行 | 问题、选项、预测、训练反馈、任务类型、完整轨迹索引、工具参数、观察和停止原因 | 确定问题现象和发生位置 |
| 视觉与数据能力 | 实际帧索引/时间/尺寸/变换、采样间隔、reader 类型、可访问上限、字幕与时间映射 | 判断证据覆盖；知道哪些动作可执行 |
| 诊断与对照 | 多原因假设、支持/反例、成功且高效案例、主动调查及同前缀续跑结果 | 将现象与修改方向关联，避免从对错直接跳到方案 |
| 成本明细 | 每题和每阶段 token、调用/重试/异常、延迟、分位数、usage 完整性 | 估计完整任务代价，发现重复上下文和无效观察 |
| 历史 Task 尝试 | 补丁、父版本、假设、诊断集结果、选择集聚合结果、接受/拒绝原因、兼容性问题 | 避免重复失败，保留成功行为 |
| 固定契约与资源 | 可改文件/字段、禁止路径、依赖、必检、候选数、剩余 token/运行预算 | 约束可执行产物和搜索成本 |

全量原始记录落盘，模型输入由预算内的当前摘要、代表性证据、支持/反例和相关源码组成，提供按 ID 读取原始诊断资料的入口。不能只给一段“准确率低”的汇总，也不必把所有历史图片塞入 prompt。

诊断/训练标签可用于评估原因，但不能放进视觉调查查询或候选运行时提示。Task 选择集只提供聚合及预先声明的分任务统计；逐题标签、轨迹和测试数据不交给 proposer。所有摘要与源码中去除凭据。

## 8. G 生成 Meta 候选所需输入

只有 Task 轨迹不足以改进 M：必须记录 M 当时看到了什么、做了什么，以及后续真实结果。

| 信息包 | 必需内容 |
|---|---|
| 当前 Meta 快照 | M ID、诊断/提案代码与提示、输入组装、分组与预算配置、接口和依赖 |
| Task 起点 | 各次进化的 Task 父版本、模型、数据能力和环境指纹，防止把容易起点与困难起点混为一谈 |
| 进化过程完整记录 | 案例选择、proposer 实际输入、诊断、调查、候选补丁、局部修复、预检、选择结果及全部成本 |
| 预期与实际差异 | 候选预测改善的机制、实测质量/成本、受损类别、失败或无更新原因、不确定性 |
| 多轮搜索结果 | 固定预算下 Task 最终成绩、改进曲线、首次有效修改成本、有效候选率、编译/运行失败率 |
| 跨批次证据 | 不同任务族和起点上的表现；有效修改、无效修改、昂贵成功和便宜失败的对照 |
| Meta 历史 | 旧 M 补丁、外层验证汇总、失败原因、成本、尚未验证的假设 |
| 外层固定规则 | Meta 可改范围、内层运行预算、强制验证、数据访问边界、剩余外层预算 |

接受率和生成代码成功率只是诊断指标。一个只提出保守无收益修改的 M 可能有很高接受率，不能因此被判定更好。Meta 的主要收益是同等内层预算下得到更好的 Task 程序，或以更少成本达到预先定义的 Task 质量与成本目标。

初始外层更新器 G 固定：比较多次进化的预期—实际差异，选择一个反复出现且证据支持的进化缺陷，生成对诊断/提案模块的补丁及预测行为变化，再交给 V_M。

## 9. 两类候选的输出契约

生成候选必须有实际源码补丁；提示和配置也版本化，单独“建议改进”不算程序候选。生成器不自行发布或宣布通过。

```json
{
  "candidate_id": "unique-id",
  "layer": "task-or-meta",
  "parent_id": "exact-parent-version",
  "generator_version": "M-id-or-fixed-G-id",
  "hypothesis": "mechanism-to-change-and-expected-effect",
  "evidence_refs": ["record-id/message-id", "investigation-id"],
  "patch_path": "candidate/source.patch",
  "config_patch_path": "candidate/config.patch.json",
  "asset_manifest_path": "candidate/assets.json",
  "changed_modules": ["allowed/module.py"],
  "runtime_trigger": "deployment-visible-condition-or-not-applicable",
  "expected_quality_change": "prediction-with-uncertainty",
  "expected_cost_change": "prediction-with-uncertainty",
  "regression_risks": ["taYOUR_API_KEY"],
  "local_check_plan": ["case-ids-and-counterexamples"]
}
```

`asset_manifest` 记录 Skill/Memory 等是否改变及哈希。验证结果另写固定报告，包含完整执行结果、真实成本、异常、所有强制检查和最终接受理由。`expected_*` 不参与计量替代。

## 10. Meta 初始更新与验证流程

1. 用固定 M_s 完成若干 Task 进化轮次，归档全部尝试，不只成功轮次。
2. G 读取第 8 节信息，为进化器产生 M'；外层固定检查首先验证接口与修改范围。
3. 在多个预先指定的 Task 起点、任务批次和种子上，分别运行 M_s 与 M'，内层使用相同模型、候选验证器、总预算和数据访问条件。
4. 每个分支均从同一 Task 快照开始，使用独立工作目录，不能把旧 M 的改进后版本只提供给新 M；起点可包括 T0 和较成熟的 T，以检查改进是否只在早期有效。
5. 内层可自由选择诊断案例和候选，但不能改变外部预算及必检。计入被拒绝候选、重试、调查和局部修复；超预算的候选不能继续争取额外比较优势。
6. 比较固定预算下 Task 最终质量—成本结果、不同任务类别退化和跨批次稳定性。候选优化时只能读取外层允许的聚合反馈，不能读取外层保留任务的逐题标签。
7. 固定 V_M 接受或拒绝 M'。只有接受后才用于后续正式 Task 进化；正式 Task 当前版本独立保留，外层验证分支的 Task 产物不自动晋升。

严格版本的数据用途包括内层诊断/拟合集、Task 选择集、外层进化器保留任务批次和最终测试集。按来源视频隔离，EgoLife 等还遵守主体和时间约束。外层验证任务仍可各自划分内层诊断与选择部分；其逐题数据不进入 G 的拟合输入。反复读取聚合反馈仍可能过拟合，需固定外层搜索预算并保留最终独立测试。

M' 的收益需通过重新运行内层进化验证，不能只在旧档案上重新解释，也不能仅比较 proposer 的文字质量。匹配的是总搜索成本，不是相同轮数；固定各角色模型后 token 可作为资源代理，同时报告运行数和延迟。双层方法的总实验成本还须包括生成和验证 M' 的额外支出。

## 11. 一个跨两层的候选例子

Task 现象：短动作题错误。M 提出增加 `clip_skim` 帧数。局部部分修复，但其他区间仍错且总成本上升。

Task 诊断候选：保留时间覆盖，在明确的动作候选附近增加采样；同时保留成功区间作为反例。其收益须完整 QA 验证。

Meta 现象：多轮 proposer 都从“答错”直接推到“帧数不足”，未检查实际采样位置与工具输出。

Meta 候选：修改诊断器，先关联帧元数据、工具观察与主 Agent 使用记录；不能区分原因时，在预算允许下比较“补看”和“仅重新推理”。修改 Task proposer 输入组装，必须携带诊断不确定项和已有成功对照。调查失败可返回未知，不强制归因。

Meta 验证：在新的任务批次上，比较两个进化器是否减少无效增帧候选，并在同预算下找到更好的 Task 程序。减少无效候选只是中间解释，最终 Task 表现仍是主要证据。

## 12. 最小实施顺序与拟议模块

下面模块均是新增建议，不是现有文件：

```text
videospy/runtime_policy.py              # 可进化 Task 决策策略
videospy/evidence_policy.py             # 可进化 Task 工作上下文
videospy/rsi/task_loop.py               # 固定内层流程包装器
videospy/rsi/meta/diagnoser.py           # 首版可进化
videospy/rsi/meta/task_proposer.py       # 首版可进化
videospy/rsi/meta/case_selector.py       # 首版固定，后续开放
videospy/rsi/meta/investigator.py        # 首版固定，后续开放
videospy/rsi/meta/search_scheduler.py    # 首版固定，后续开放
videospy/rsi/outer_updater.py            # 固定 G
videospy/rsi/meta_loop.py                # 固定外层流程包装器
videospy/rsi/validation/                # 固定验证/权限/接受规则
videospy/rsi/archive.py                 # 固定版本和尝试档案
```

先补结构化帧元数据、全调用记录与成本归因，抽出 Task 可改边界，再实现固定 M0 的 Task RSI。确认完整生成—执行—选择闭环有效后，积累进化记录，开放诊断器与 proposer 的 Meta 更新。

既有 SQLite 继续保存经验资产，通过源码/配置 manifest 与 Task 版本绑定；第一版无需把整套源码写入原经验表。M 的历史索引和经验独立保存，不能混入当前事实 Memory。

最小对照：基础版；当前 Skill/Memory 进化；固定 M0 的 Task 程序 RSI；双层 RSI。匹配总离线成本，固定模型和数据权限。另区分工具代码、执行策略、经验文档的贡献，防止把所有收益归于 Meta。

本稿的首要待验证假设是：对 Task 进化过程的可执行改进，能在新任务批次上提高有限预算内的程序搜索效果。两层命名及更复杂的架构本身不构成这一结论。
