# V20：离线进化的质量与使用方式改进方案

本方案基于 `output/train_offline_V19` 中三个 lite 实验及后续 debug/lite 对照迭代。当前改进涉及 Skill 的证据审核与容量管理，以及 Memory 的来源限制、时间线恢复和检查位置展示。Agent 主推理流程与训练脚本保持不变。尚未验证稳定的推理收益或 Skill 与 Memory 的叠加收益，最近实现与验证情况见第 10 节。

## 1. 结论与目标边界

V19 的主要问题不是没有并行，也不是没有正确加载成果，而是**学习目标、产物约束和使用条件没有形成一致的约束**：

1. 综合分数和相对 Good/Bad 可以发现较好的轨迹，但不能证明其中的决策正确、可迁移。逐组重写会累加错误规则，也会长期保留第一组的狭窄经验。
2. Skill 没有长度预算，`applies_when` 也不限制加载。多个 Task Skill 和 Domain Skill 全量拼接，既增加每轮输入成本，也容易形成相互冲突的操作要求。
3. Memory 提取的是局部视频事实，检索却允许仅凭问题相似度跨视频使用。事实的来源被展示出来，并不等于模型会正确处理其适用范围。
4. Memory 的引用格式失败很多，成功引用也只证明文本存在。工具输出中的推测、全局否定和错误时间解释仍可能被保存。
5. 当前结果存在明显的运行波动。尤其是未命中 Memory 的题目，也产生大量答案变化。单次消融差值不足以判断真实收益。

V20 的目标仍是准确率提高、推理轮数和 Token 降低，但应当作为需要实验验证的目标。不能承诺每次逐组更新都改进，也不能假定 Skill 与 Memory 的收益必然相加。

**需要明确的研究边界：**如果 Memory 继续定义为有来源的视频事实，那么它主要解决同一视频或同一人物时间线中的事实复用。当前 LVBench、MedVidBench 的记忆来源视频与测试视频没有交集，严格限制来源后，这两组实验可能基本不使用 Memory。这是正确的适用性判断，不能宣称为 Memory 带来了正收益。若要求 Memory 在完全不同的视频上也稳定提升，需要另外定义和验证可迁移知识或案例记忆，不能在本轮悄悄把事实 Memory 改成第二套 Skill。

## 2. 本次实验实际说明了什么

### 2.1 数据来源与对比口径

三个运行均位于 `output/train_offline_V19/experiments/train/<benchmark>/lite/`：

|---|---|---:|---:|
| LVBench | `self_openai_Qwen3.5-4B_20260910_195523_c9e0aac` | 412 | 105 |
| EgoLife | `self_openai_Qwen3.5-4B_20260910_195632_c9e0aac` | 135 | 32 |
| MedVidBench | `self_openai_Qwen3.5-4B_20260910_195554_c9e0aac` | 503 | 113 |

依据各运行的 `offline_result.json`、`reflection/classification.json`、`reflection/selection.json`、最终 `skills.json` / `memories.json`，以及四组评测的 `run.json`、`records.jsonl`、`report.md` 和实际轨迹进行核对。MedVidBench 另有 12 条源推理失败，503 是有效来源数，不是预期抽样总数 515。

核对结果：

- 每个 benchmark 的四组评测使用相同的题目清单、模型和基础推理配置。Agent 与视觉工具的参数没有随着消融组改变。训练与测试 sample ID 无交集。
- 实际轨迹中的组件加载符合消融开关。Skill Only / Base 没有注入 Memory，Memory Only 没有注入 Skill。
- 模型配置为 `openai/Qwen3.5-4B`，记录的 Agent temperature 为 0、seed 为 42，但运行结果仍有明显波动。
- 旧训练来源与本轮评测策略不同。三组 `evolution.log` 均记录了 SYSTEM_PROMPT 差异，LVBench、MedVidBench 还记录 Agent 和视觉工具 temperature 从 1.0 变为 0.0。它不破坏本轮四组评测之间的配置一致性，但会影响旧失败经验对当前 Agent 的适用性。
- LVBench Base 和 Skill Only 各有一道推理失败，均为样本 `4762`。准确率以全部 105 题为分母，成本表沿用 report.md 的全部记录口径，不能只统计成功题并与原报告混用。

### 2.3 必须先处理的归因问题

根据实际系统提示中是否存在 Memory，将 Memory Only 分层，与相同题目的 Base 配对：

| Benchmark | Memory 是否命中 | 题数 | Base 答对 | Memory Only 答对 | 预测发生变化 |
|---|---|---:|---:|---:|---:|
| EgoLife | 否 | 8 | 1 | 6 | 6 |
| EgoLife | 是 | 24 | 4 | 4 | 14 |
| LVBench | 否 | 66 | 24 | 22 | 29 |
| LVBench | 是 | 39 | 21 | 21 | 18 |

所有未命中题目的初始 system/user 消息都与对应 Base 完全相同。EgoLife Memory Only 的总净增益 5 题全部来自未命中子集，LVBench 的总净损失 2 题也来自未命中子集。命中子集总答对数不变，内部仍有题目改善和退化。

这说明**当前单次结果不能把这部分变化归因于 Memory 内容**。可以确认输入相同而结果变化，不能仅凭现有日志确定是服务端批处理、数值非确定性、视觉工具输出波动还是其他运行因素。temperature=0 和固定 seed 不足以替代重复实验。

LVBench Skill Only 相比 Base 是 14 题由错变对、16 题由对变错。组合则是 16 题改善、20 题退化。只看总准确率，会漏掉这种较大的逐题变化。

## 3. 现在学到了什么，为什么没有达到预期

### 3.1 已经做对的部分

- 双通路成立。Others 和分类失败不会切断 Memory，单条失败不会丢弃其他成果。
- 最终保持每任务一个 Skill，另有一个 Domain Skill。当前问题不在于把所有 group 文件都当成 Skill 加载。
- 分类按任务归一化，多标签轨迹复用一次评分，分组和 Futures 的组织符合 V19 约定。
- 学到了部分有价值的决策方向，例如定位候选区间后再检查关键帧、区分动作执行与静止保持、避免重复检查、在证据充分时停止。
- Memory 保存来源、事件、时间、不确定性和引用，EgoLife 还做了来源时间过滤。这些基础应保留。
- 检查点、失败统计和实际轨迹支持追溯。后续 debug 暴露证据语义错配，因此在既有反思末尾增加一次发布前核对，不增加逐组审核或反复总结。

### 3.2 Classification 的相对分组不能充当成功证明

本次 EgoLife EventRecall 的任务均分约 0.319，0.4 分就会进入 Good，8 条 Good 中有 3 条答案错误。LVBench entity recognition 的 64 条 Good 中有 11 条答案错误，summarization 的 4 条 Good 中有 2 条答案错误。这不违反 V19 的相对分类定义，但说明不能直接从 Good 轨迹复制其结论或决策。

例如 EgoLife 训练样本 `247` 以 0.4 分进入 Good，理由同时包含参考答案是 takeout、观察倾向 package、最终推断薄弱等内容。Reflector 看到的是矛盾信息，而不是清晰的正例。

同任务分组也不保证每组存在可学习的成功做法。LVBench 有 36/137 组全 Bad，EgoLife 有 12/32 组全 Bad，MedVidBench 有 15/118 组全 Bad。允许一侧补齐是合理的，但全 Bad 组应主要总结有依据的失败规避，不能凭空生成最佳方案。

评分与反思主要读取视觉工具生成的文本，没有重新核对视频。成功执行工具只表示请求成功，不表示描述正确。参考答案可以揭示错误结果，但不能证明它没有展示的视觉细节。单一分数也无法明确表达“答案错误，但定位方法有用”和“答案正确，但依赖猜测”的区别。

还存在观察覆盖的上限：当前 overview 每次只均匀采样 64 帧。EgoLife 测试题 `409` 的可用拼接时间线约 135,096 秒，一次 overview 的采样间隔约为 36 分钟视频时间，难以覆盖短暂事件。反思不能从没有观察到的信息中恢复事实。V20 先改进如何利用已有证据，不把更换视觉模型或增加采样量混入同一个消融；若之后仍受此限制，再作为单独的观察策略问题研究。

### 3.3 Skill 会膨胀，也会被早期样本固定住

| 实际系统提示平均字符数 | Base | Skill | Memory | Skill + Memory |
|---|---:|---:|---:|---:|
| LVBench | 5,832 | 24,090 | 6,485 | 24,663 |
| EgoLife | 5,832 | 13,080 | 7,493 | 14,742 |
| MedVidBench | 5,832 | 11,962 | 9,550 | 15,681 |

这是轨迹中实际注入的字符数，不是 tokenizer 计算的 Token。LVBench Skill Only 最长系统提示达到 48,317 字符。其 entity recognition 的 instruction 为 9,470 字符，条件列表又有 9,640 字符；reasoning 的 instruction 为 13,742 字符，条件列表又有 4,568 字符。

LVBench reasoning 的 instruction 加条件从第一组 1,664 字符增长到最终 18,310 字符。长提示在每轮 Agent 请求中重复出现。全部实验的累计输入 Token 占比约 95%～97%，因此产物膨胀是明确的成本来源，但不能将全部 Token 增量都归因于 Skill，工具次数和观察长度也会变化。

相反，MedVidBench next_action 处理了 13 组后，仍主要保留第一组的 ESD 组织瓣与刀具定位经验。它可以对这个条件下的任务有用，却不等于覆盖整个 next_action。当前 `source_sample_ids` 随每次非空输出并入整组 ID，最终显示 52 个来源，不能解释为这条经验受到 52 个样本独立支持。

需要区分两种失败：累加式更新造成冗长，保守照抄造成覆盖不足。单纯把已有长段落压缩一次不能同时解决它们。

### 3.4 产物中存在不应泛化的规则

可在各运行的 `reflection/skills/tasks/` 和 `domain.json` 中直接复核：

- EgoLife EntityLog / Domain 将工具没有提到目标归纳为立即停止或事件不存在。稀疏采样不支持这种全局否定。
- EgoLife HabitInsight 从实体店场景推断购物 App，RelationMap 将未提到的人优先作为否定问题答案。这些是答案捷径，不是可靠的证据策略。
- EgoLife EntityLog / EventRecall 鼓励直接用视频时间差映射“几小时前”，但当前输入秒数来自去除录制间隙后的拼接时间线，并不等于真实经过时间。
- LVBench Domain 将视觉描述作为唯一事实来源，压低了字幕、台词或屏幕文字在某些问题中的作用。reasoning 的规则还要求继续检查相邻片段，容易将证据要求变成额外搜索。
- MedVidBench STG 同时出现按视角推断左右手、不可见时预测位置、不可见时不编造坐标等冲突规则。Domain 还包含降低评分等表述，混入了评审口吻。

这些内容已经出现在产物中，可以确认质量风险。但现有消融不能精确分离每一条规则造成了多少准确率变化。V20 应保留该不确定性，不把个别轨迹展示为完整因果证明。

### 3.5 Memory 的领域相似度被当成了事实适用性

| Benchmark | 入库记忆 | 命中测试题 | 注入记忆条次 | 注入条次中同视频 / 同时间线 |
|---|---:|---:|---:|---:|
| LVBench | 221 | 39/105 | 80 | 0/80 |
| EgoLife | 60 | 24/32 | 58 | 58/58，同一 A1_JAKE 时间线 |
| MedVidBench | 211 | 113/113 | 339 | 0/339 |

Memory Only 和 Skill + Memory 的命中内容一致。LVBench 测试涉及 20 个视频，记忆来自 79 个视频，两者无交集；MedVidBench 测试涉及 53 个视频，记忆来自 102 个视频，两者也无交集。

具体例子：

- LVBench 测试题 `2251` 问麦克风支架颜色，检索到另一个视频中粉色标牌上写着 FLOOR 的事实。词面相关没有建立场景关系。该题的 Base / Skill / Memory / 组合预测分别为 C / D / D / B，说明需要逐题分析，不能只凭这个例子断言 Memory 造成了哪一种错误。
- MedVidBench 测试题 `1546` 问当前视频 Secure the base 的时间范围，注入的三条记忆来自其他视频，带有各自局部片段的 17～23 秒等时间。即使动作名称一致，也不能作为本题边界。Base 用 3 轮，Memory 用 10 轮，Skill 和组合各用 17 轮。
- EgoLife 测试题 `439` 问 Lucia 可能拍卖什么，检索到她评论烘焙食品、组装抽屉和投票选择饮料的历史。人物相同、来源合法，仍不足以说明事件相同。

代码原因：`memory_available()` 对非 EgoLife 直接放行；Agent 检索传入 `task_types=None`；LVBench 适配器尚未设置明确的 `memory_context`。Query 还包括回答格式及部分模板说明，索引混合 context/content/event，容易被相同领域词汇或人物名称主导。`similarity_threshold=0.5`、Top K=3 只是相似度和数量约束，不是事实适用性检查。

### 3.6 Memory 的覆盖、局部性和时间问题

| Benchmark | 提取成功，含 null | 提取失败 | 其中引用不连续 / 超长 | 合法 null | 最终入库 |
|---|---:|---:|---:|---:|---:|
| LVBench | 251/412 | 161，39.1% | 123 / 30 | 30 | 221 |
| EgoLife | 75/135 | 60，44.4% | 45 / 12 | 15 | 60 |
| MedVidBench | 215/503 | 288，57.3% | 221 / 56 | 4 | 211 |

各组去重数均为 0，但这不证明去重失效或所有记忆都有效。许多来源、事件区间不同，本就不应合并。LVBench / EgoLife / MedVidBench 分别有 33 / 11 / 26 条记忆缺少完整数值区间。

还存在更隐蔽的语义问题。例如 EgoLife 记忆 `source_sample_id=295` 把 61815.1 秒附近的一次食物讨论表述为最后一次讨论，引用来自工具总结。它只支持已找到的一次事件，不证明后续没有其他事件。新问题时刻变化后，“最后一次”也可能失效。

EgoLife 有 12 条记忆的 time.label 包含来源 query_time 的完整时间字符串。不能据此逐条判定错误，因为事件可能恰好发生于查询附近，但程序没有验证这种等同。`source.query_time` 已由程序固定，**事件时间 label 仍可由模型自行填写**，所以可用时间安全不等于事件时间正确。

`EgoLifeTimelineReader` 将录制片段拼接并移除间隙。当前程序只有日历时间到视频秒数的映射，不能让模型直接相减拼接秒数去回答日历时间差。事件坐标、真实发生时间、记忆可用时间应当分别处理。

最后，Agent 在没有初始字幕时仍要求至少一次成功视觉调用，Memory 不计入该门槛。这个保护不是错误，但意味着当前 Memory 更适合直接定位一次检查，不能自动兑现“读到记忆后零视觉调用”。

## 4. V20 保留什么，改变什么

保留：离线来源、full/lite/debug、现有采样配置、每轨迹一次分类、每任务归一化、Good/Bad 分组、每任务一个 Skill、一个 Domain Skill、每轨迹最多一条 Memory、Futures/WORKERS、tqdm、失败继续、JSON/SQLite 和检查点。

明确改变 V19 的三项规则：

1. 相对 Good 不再被用作正向决策的充分条件，反思同时读取绝对结果与证据支持情况。
2. Skill 从无界长文改成长度受限、带来源的条件规则，在原有逐组更新中积累有效支持与反例，迭代结束后筛选任务最佳实践。
3. 事实 Memory 默认只在可比较的来源内检索，跨视频仅相似不再足以注入。

不增加 findings、在线训练、Memory 语义审核、检索重排模型或按时间重训 Skill。每任务一次 Skill 发布前核对是本轮确认的新调整，取代之前完全不增加模型审核的约定。不通过调大 max_steps、换更强模型或放宽证据要求掩盖算法问题。

## 5. 训练端：让 Skill 归纳目标可解释

### 5.1 分类仍只请求一次，补充必要的区分

保留 `score`、`reason` 和当前 z-score 分组。分类结果增加两个小字段：

- `answer_status`：`correct / incorrect / unverified`。LVBench、EgoLife 用已有标准化预测与参考选项由程序确定，模型不能覆盖。MedVidBench 只在可靠的结构化规则可判断时由程序确定，其余由同一次分类请求给出判断，无法可靠判断则 unverified，并记录判断来源。不新增官方评测或额外 Judge 前置阶段，也不将 NAP 的本地精确匹配冒充官方正确性。
- `evidence_support`：`sufficient / partial / insufficient`，由同一次分类请求根据可读观察给出。它是评估结论，不是视觉事实核验。

在评分输入中加入已有记录里的轮数、累计 Token、finish_reason 和成功/失败工具次数。没有记录的指标留空，不能当作零。保持综合评分语义：只有结果和证据成立后，较少无效动作才是优点，不以固定轮数越小越好来奖励猜测。

分组算法及 bad_ratio 不变。Skill 反思时明确：

- 只有 answer_status=correct 且 evidence_support=sufficient 的轨迹，才可提供正向决策示范。
- 错误或不充分轨迹仍有用，可以支持失败规避、定位方法或需要补齐的证据缺口。不能从其最终错误选项归纳事实或选择偏好。
- 全 Bad、全不充分组允许返回 null。纠正原则必须由观察和失败机制支持，不能因为没有正例就编造成功策略。
- 参考答案只用于评价结果，不能作为 Memory 事实或 Skill 中的场景答案。分类理由也不是独立观察。

这一改动不是重新设计评分公式。先消除正例含义不清，再判断是否需要更复杂的多目标评分。首轮不引入未经标定的评分权重。

### 5.2 每个 Skill 内保存少量条件规则

同任务仍逐组更新一个 Skill，但模型返回结构化 rules，不再自由追加长段落。训练中保留一个有界的工作 Skill，用来积累和比较经验；结束后从中选出更精简的最终 Skill，用于推理。两者是同一任务 Skill 的训练状态与发布结果，不是两套独立生成通路：

```json
{
  "rules": [
    {
      "when": "已定位候选事件，但相邻两个答案仍有一个可观察差异",
      "action": "检查能区分这两个答案的候选时刻，复用已有观察",
      "stop": "已有观察足以区分答案后停止，不因规则存在而重复检查",
      "condition_clear": true,
      "evidence": [
        {"sample_id": "sample_a", "role": "supports", "message_index": 3,
         "reason": "该决策如何支持规则，以及适用条件为何成立"}
      ]
    }
  ],
  "remove_ids": []
}
```

这是数据结构示意，不直接放入模型提示作为答案示例。实际提示给出字段要求和空值 JSON 骨架，避免复制示例中的具体经验。

首轮规则约束：

- 训练中的工作 Task Skill 最多 10 条规则，全部 when/action/stop 合计不超过 3,600 字符；最终 Task Skill 最多 5 条、合计不超过 1,800 字符。稍大的工作容量用于等待后续样本支持新经验，不把首次出现的经验立即淘汰。Domain 最多 3 条，合计不超过 600 字符。先用可确定计算的字符预算，无需增加 tokenizer 依赖，实际 Token 另外测量。
- 每条规则表达一个有条件的决策和停止条件。不写样本答案、专名猜测、当前视频时间、逐组改进记录或泛化的手术常识。不把穷尽搜索作为默认套路，追加搜索应有明确的证据缺口和预期新增信息，反复无收益搜索只能作为失败依据。
- 组内先识别正确且证据充分轨迹中的有效决策，再归纳动作前可识别的条件、针对性动作和动作后的停止条件。触发条件不能要求已知答案或已完成该动作。不同方法可独立保留，不把新样本强行套入旧规则，也不因同属 Task 或调用相同工具而合并。优先引用体现决策和观察的消息，避免只引用最终选项字母。
- 不以 overview / frame_inspect 的名称建立固定可信度排序。依据具体观察是否直接、清晰、相关、有冲突来选择证据。
- 不将未采样、未提及等同于不存在，不将字幕中的说话人自动等同于动作执行者，也不从模糊姿态推断身份。
- 每次只返回新增或更新的 rules。未提及的旧规则自动保留，删除必须通过 `remove_ids` 明确指定；`merge_ids` 消费被合并的旧规则。容量限制针对合并后的完整工作状态，超限时在原有一次纠错中要求明确删除或合并，不静默丢弃历史。
- 新规则不填写 ID，由程序生成，后续更新引用已有 ID。缺少 ID 或仅填临时名称时，如果 when/action/stop 经空白规范化后与唯一旧规则完全相同，程序恢复旧 ID 并累计依据；不存在的 `rule:` 引用仍报错。只改变措辞时由模型引用旧 ID；改变条件或决策则作为新规则重新积累证据，旧规则需要删除时另行声明。不得同时删除又重建文字完全相同的规则来清空反例。完全相同的文本与依据记为未变化，文本不变但新增有效依据则只更新统计。
- 新经验可以凭一条结构校验通过的依据进入工作 Skill。发布不再要求两条支持：正向做法有一条核对通过且符合 5.1 的正例即可参与筛选，纯失败规避有一条匹配的失败案例即可。纯失败规避每任务仍最多一条，不能声称某个未执行策略已获验证。支持次数用于排序，失败案例不计入成功支持数，没有有效依据的规则不发布。
- 同一视频的多道题不算跨视频迁移证明。规则的来源多样性写入摘要，首轮不增加第二套强制抽样流程。
- 旧规则在组内没有新增依据时保留，但不能把整组 ID 自动计作支持。新增依据携带 `sample_id`、`role`、`message_index` 和 `reason`，程序绑定完整原始 assistant/tool 消息，模型无需抄写 quote。reason 要求非空、提示简短。历史原始消息不随每组更新反复输入，但在发布前统一送入核对；最终 `source_sample_ids` 仅汇总发布规则中核对通过的引用。
- 引用错误只拒绝该条依据，仍有有效依据的规则可以继续更新；规则格式或身份错误只拒绝该条规则，其旧状态保留。全部新引用无效时不能借用旧依据批准改写。有效更新保存在检查点，拒绝明细和原始响应同时保留，摘要记录 rejected_rules/rejected_evidence 并标记 partial。局部拒绝视为本次已处理的决策，续跑复用它及拒绝明细，不重复请求整个成功分组；这与整组请求失败后续跑补齐不同。
- 无有效更新而存在拒绝、顶层 JSON 错误或合并后超预算时，沿用一次纠正机制，仍失败则保留此前工作状态并 warning。合法无更新返回 null。发布前核对成功但规则被正常淘汰，允许无 Skill 评测并明确组件未生效；没有成功核对且 Task 反思失败、无可用规则时继续阻止自动消融。旧发布产物不能绕过核对成为兜底。

规则来源只证明反思依据可追溯，不证明因果改善。程序不会通过字符串黑名单声称完成语义审核，实际质量仍需产物检查和验证集评测。

为保证改动集中，`instruction` 由最终 rules 确定性渲染，不能让模型再输出一份独立长文。取消冗长的全局 applies_when 拼接。工作 Skill 的规则、依据和状态保存在原有逐组检查点，最终 JSON/SQLite 保存入选规则及其统计。续跑恢复工作状态，不拿已压缩的最终 Skill 重新开始累计。需要改动的是 Skill 的存取和渲染，不重新设计整套数据库，不为旧 V19 产物增加兼容转换。

### 5.3 迭代中积累统计，结束后筛选任务最佳实践

最终 Skill 应保留有有效依据、适用条件清楚、能指导有效决策的经验。分组反思累计候选依据，发布前按任务统一核对一次，再由程序重算有效统计，不做全量反复总结。

首先分清三个不同的数量：

| 数量 | 能说明什么 | 本轮是否用于筛选 |
|---|---|---|
| 模型重复写出某条经验的次数 | 可能只是沿用旧文本或偏好某种措辞 | 否，不作为支持 |
| 不同训练轨迹对经验的有效支持数 | 该经验在已检查样本中有多少依据 | 是，由程序去重累计 |
| 推理时实际采用规则且产生收益的次数 | 需要实际评测和行为归因 | 本轮不假定已知，加载次数不能替代 |

**每组更新时，模型识别证据关系，程序负责累计。** 现有请求输入本组轨迹、工作 Skill 和各规则的简短统计，输出更新后的规则，以及本组哪些轨迹与哪些规则相关。不让模型直接填写累计次数。关系分为：

- `supports`：轨迹实际体现了该决策，且满足 5.1 的正例条件。仅在成功轨迹里出现类似措辞，不足以作为支持。
- `failure_example`：轨迹暴露了该规则试图避免的具体失败，但没有证明执行该规则就一定成功。这类依据支持失败规避，不计入成功支持数。
- `contradicts`：在规则所声明的条件下，观察揭示了规则不适用或导致错误的具体原因。轨迹答错不自动构成该规则的反例，需要明确关联。
- 无法判断或与规则无关时不关联，不把本组所有轨迹都计入。

程序按每任务的 `rule_id + sample_id` 记录证据关系，同一轨迹的重复引用、检查点复用和续跑都只算一次。一条轨迹不能在同一规则下同时充当成功支持和矛盾反例。语义相同的规则在原有更新中合并，程序对来源集合取并集，不能把两个计数直接相加。语义是否等价仍是本次反思的判断，程序检查消息位置、集合与计数一致性，不宣称自动完成了语义核验。输入中直接列出各轨迹允许的依据角色，非法 supports 的拒绝信息包含具体 sample ID、答案状态及证据状态，不能自动改成 failure_example 来通过校验。

每条规则保留成功支持数、失败案例数、矛盾反例数、独立来源数和首次出现的组号，原始 sample ID 集合保留供追溯。统计由集合推导，不作为另一份可独立修改的状态：

- LVBench / MedVidBench 的独立来源按原视频计数，同一视频的不同题目或不同片段不能冒充多个独立视频。
- EgoLife 只有一个主体时间线，改为统计有可靠事件区间、互不重叠的事件来源。事件身份无法可靠区分时，只报告轨迹数，不虚构独立事件数。
- 关联轨迹的轮数与 Token 可作为成本描述，但不是这条规则带来的节省，也不以不同难度题目的原始平均成本直接排序。

**迭代结束后，每任务核对一次，再由程序筛选，不调用模型重写。** 组内次数是待核对的候选统计，核对当前规则全文与全部历史引用后，才得到最终有效统计。

核对输入包括最多 10 条最终工作规则、引用对应问题与来源、分类状态、程序绑定的步骤数、结束原因和成本。原始引用补充前后相邻 Agent 决策及其工具请求、观察，并按原消息索引去重，不传参考答案或把分类理由当作证据。不裁剪选中消息的文本；这些是局部上下文，未选中的历史事件属于未知，不能据此判断从未执行。上下文消息不增加新的样本引用。

核对按动作前的 when 和动作后的 stop 判断适用性，先遇到歧义再成功解决可以支持相应规则，不要求结束时仍存在歧义。`reach_max_steps` 证明达到步骤预算，不证明已穷尽视频搜索。失败案例可以支持针对该机制的规避策略，不要求失败轨迹已经执行补救动作，也不能把这种依据计成已验证成功。

每条规则必须输出 `keep / drop / uncertain` 和简短理由。对于 keep，全部 sample ID 引用逐一判断，缺项不能默认通过。对于 drop 或 uncertain，允许 `evidence: []`，程序整体排除其引用，并用 `excluded_by_rule` 记录原因来自规则级决策，不虚构逐引用语义判断。全部规则放在一个 rules 数组，每个引用使用独立对象，理由只给一句结论，不展开反复推演。JSON 解码拒绝重复键并进入原有一次格式纠正，避免后一个 rules 或 sample_id 静默覆盖前一个。只允许删除，不允许改写规则、增加引用或变更角色；未知、重复 ID 以及保留规则缺失引用判断进入原有一次格式纠正，错误信息列出缺失 ID。`uncertain` 不发布、不计数。场景答案、未观察到即不存在、错误时间换算、无效重复搜索及不满足当前规则条件的引用应被排除。模型核对仍不是重新查看视频或证明观察正确。

程序根据核对后引用重算 stats/source_sample_ids，核对决策与 before/after 统计写入 review 检查点和最终 Skill 的 review 字段。淘汰引用数按核对前后实际集合数量计算，整条删除且不逐引用判断时也完整计数。改写、合并后的规则按当前全文核对，不能直接继承有效支持。核对与发布都不因只有一条有效依据而淘汰方法，后续筛选执行：

1. 排除核对淘汰、没有有效依据、条件不清或存在有效矛盾反例的规则。一条有效正例或匹配的失败案例即可进入后续筛选。核对不把错误角色改成另一角色，不为了保留高频规则抹去反例。
2. 正向最佳实践与纯失败规避分开比较。正向经验优先看独立来源数，再看成功支持数；失败规避看对应失败机制的独立来源与案例数，不能把大量错误样本当作成功支持。
3. 首轮在最多 5 条的最终 Skill 中，最多保留 1 条有充分依据的纯失败规避，其余优先保留正向实践。没有合格经验时少保留或不发布，不为填满名额降低要求。同分时按稳定 ID 排序，避免并发或字典顺序改变结果。
4. 在字符预算内按完整规则保留，最终排序与选择结果写入产物。只有通过这一步的规则进入推理提示，统计和淘汰原因不进入提示。

这是一种简单、可复现的筛选方式，不引入多个评分权重。频率决定的是已有有效经验中的优先级，不能覆盖质量要求。只出现一次的经验通过语义核对也可发布，但单例不证明跨样本泛化收益。通用的不得编造证据、必须遵循输出格式等基础约束继续由基础提示保证，不依赖训练频次竞争名额。

还要明确统计的局限：经验较晚出现时，并未被系统性地与此前每条轨迹核对；Good/Bad 分组和 max_samples 也改变了看到的样本分布。因此这里只统计**已明确关联的训练依据**，不宣称是全数据集使用率或规则成功率。工作 Skill 的容量也可能淘汰后来有用的经验，检查点保留其历史；首轮接受这个有界近似，验证时用固定的不同分组顺序检查最终规则和收益是否稳定，不增加全量回扫或无界经验库。

### 5.4 Domain 只保留跨任务共性

- 仍在各 Task Skill 完成后请求一次。
- Domain 生成最多 3 条候选规则，候选文本总量最多 1,800 字符，提示每条尽量简短并按重要性排序。程序按此顺序选择完整规则，最终 when/action/stop 合计仍不超过 600 字符。超过剩余预算的规则跳过，继续检查后面的规则，不截断半条内容。最终 JSON 的 selection 记录入选、重复、条件不清或预算不足等原因。
- 以最终筛选后的 Task Skill 为输入，并提供简短支持统计。每条 Domain 规则注明依据的 Task 规则，至少来自两个不同任务。不把单任务场景经验提升为领域规律，也不因某个任务样本多就把它的规则当成领域共性。
- 不重复基础提示已有的工具数量限制、输出格式等通用说明，不再追加大段必须检查的要求。
- 同时加载时，对文本完全相同的规则做确定性去重。语义上的压缩和去重在原本的 Domain 请求内完成，不再加一次总结请求。
- 没有跨任务共性时允许没有 Domain Skill。错误或 null 仅能保留来源仍有效的旧结果：引用仍覆盖两个已发布任务，且对应 Task 规则文本指纹未变。旧产物没有该核对信息时不能兜底，已淘汰规则不能经由旧 Domain 回到推理。
- 如果所有可用候选单条都超过 600 字符，仍执行原有一次纠错，不能将全部超长伪装为合法无产出。格式和跨任务来源校验继续保留，不因长度筛选而放宽。
- Domain 请求失败且已有可用 Task Skill 时，整次运行标为 partial，保留失败计数、有效旧 Domain 或缺失状态，允许自动评测。摘要记录 domain_skill_available。该例外只适用于 Domain；没有可用 Task Skill 时 Domain 失败，或 Classification、Task Skill、Skill review、Memory、Embedding 任一实际执行阶段全部失败，仍标为 failed 并停止评测。代码与输入不变时续跑复用成功检查点，补齐失败节点。

### 5.5 核对的运行保障

`skill_review` 与现有任务 Future 在同一线程池中执行，每任务组内迭代结束后一次请求，复用 WORKERS、模型配置和一次格式纠正。独立 tqdm 与阶段统计记录成功、失败、空结果、跳过、复用及淘汰数量，没有候选则跳过。

`reflection/checkpoints/skills/tasks/<task>/review.json` 保存工作规则、核对决策及输入指纹，失败时也保留工作规则和响应。核对缓存身份包含规则、引用、问题、分类状态、成本与轨迹，输入变化则失效；同代码同输入续跑仅补失败项。核对失败不发布候选，不从上一轮成果绕过核对。所有规则被正常淘汰是成功无产出，不能当成模型失败。上下文超限明确失败，不裁剪原始引用，也不重试相同超长输入。

## 6. 训练端：让 Memory 更可靠、更容易提取

### 6.1 保留一条局部事实，减少模型复制负担

Memory 仍独立面向所有有效来源轨迹，每轨迹至多一条，允许 null。优先提取未来问题可能复用的具体人物、对象、动作或状态关系，而不是复述当前答案。

首轮只做以下调整：

1. 在 `evidence.py` 中将成功观察确定性切成带 ID 的原文片段，每片段不超过 400 字符。完整观察仍保留，片段可回到 tool_call_id 和原文位置，不通过裁剪丢弃输入。明确的 Conclusion、Final Answer、Categorization Analysis 等标题块标为不可选，长句被硬切出的不完整片段也不可选；这是结构过滤，不是事实核验。
2. 模型只选择一个标为 `memory_eligible=true` 的 evidence ID，evidence_ids 仍是列表，但长度必须为 1。不再生成 content、uncertainty 或手写长引用，也无需计算多段拼接长度。程序回填 evidence_refs，并将该片段原文作为 content，长度由片段生成时的不超过 400 字符保证。没有单段能独立表达有用事实及其限定语时返回 null，不截断或跨段拼接。context/event 仅作为检索问题和短标签。
3. `content` 以完整原文保留否定、推测等限定语，避免二次改写把未确认变成已确认；程序统一标注这是未经独立核验的工具观察。推理时以 Observation 展示，不把模型生成的 content 或 uncertainty 当作事实覆盖原文。模型仍应选择描述一个局部事实的片段，而不是整段工具总结；相邻观察可能共享一个片段。
4. 不把“最后一次”“经常”“从未”作为跨查询稳定事实保存。改成“在某次观察中发生了 X”。只有观察本身覆盖并明确支持频率或范围时才保留相应限定，仍不能外推到未观察区间。
5. 视觉工具推测的身份、意图和动作保持不确定性，不能通过引用回填变成已核实事实。没有清晰事实可保存就返回 null。

程序回填引用解决的是大量格式失败，不是内容核验。仍不增加独立语义审核模型。比较 V19/V20 时同时报告有效事实质量和失败率，不能以降低引用标准换取更高入库率。

提取式保存也有边界：原始工具观察本身仍可能错误，没有明确标题的答题结论也不能靠结构过滤全部识别。程序确保正文不被二次改写，并不保证每条入库内容语义正确。时间字段仍需与所选观察对应，沿用数值校验与程序绑定来源坐标。

### 6.2 时间由明确坐标管理

继续区分三种时间：

| 字段含义 | 谁负责 | 用途 |
|---|---|---|
| 事件在视频/拼接时间线中的位置 | 提取后绑定对应来源坐标 | 定位画面，不能直接当真实经过时长 |
| 事件对应的 DAY/clock 时间 | 程序使用来源时间映射换算 | 回答几小时前、昨天、先后关系等 |
| 记忆可用时间，来源 query_time | 程序固定 | 过滤当前问题之后才可用的 Memory |

EgoLife 的最小必要配套：

- 在现有 timeline 类补充由视频秒数到日历时间的公开映射方法。保留片段起点、日历起点和 Reader 实际采用的段长及其映射身份，供来源运行保存和离线训练读取。首轮沿用既有 Reader 坐标，不额外扫描全部视频重建时间线；段长假设的限制见第 10 节。
- 时间区间跨录制间隙时标明不是连续观察。边界使用与 Reader 一致的归属规则，不能把被删除的间隙补成已观察视频。
- Memory 的日期展示由程序依据事件位置生成，不再由模型复制 query_time。没有可靠映射的旧来源可以保留局部事件和视频坐标，但不生成可信日期，不允许据此计算相隔几小时。
- 推理使用记忆定位时，先确认来源和当前 timeline 映射一致。无法对应的坐标不直接作为工具参数。
- `available_at` 仍来自来源 query_time，不能因为事件发生更早就让这条记忆提前可用。本文不改变 V19 的时间泄漏防护，也不扩展按时间重训 Skill。

对“最近一次”查询，过去记忆只是候选事件和搜索起点，还需处理候选之后到当前问题之间是否存在更新事件。历史 last 标签不能直接回答新问题。

MedVidBench 保留完整帧序列与 FPS 的来源绑定，不从文件名猜跨片段偏移。无共享坐标的两段视频不能复用具体秒数。LVBench 使用标准 video_id，不能一端使用视频 ID、另一端使用绝对路径。

### 6.3 去重保持原有职责

继续只在同来源、可比较时间重叠时做文本与向量去重，时间未知时保持保守的精确去重，EgoLife 优先保留较早可用的记忆。先修复事实粒度与时间坐标，再判断是否需要改变去重算法。

不因为本次 duplicates=0 就扩大到跨视频去重，不把检索排序问题转移给去重。新的产物协议要使受影响的提取、Skill 与 Embedding 检查点失效，不能复用 V19 中已经过度概括的内容。

## 7. 推理端：只加载能帮助当前问题的内容

### 7.1 Skill 按任务加载，在规则级控制体积

- 保持按当前 task_types 读取 Task Skill 和一次 Domain Skill。没有 Task Skill 时使用现有基础策略，不补占位规则。
- 渲染 when/action/stop，不展示训练源 ID、统计、组号和历史记录。依据字段保留在 JSON/SQLite 供审计。
- 首轮全部 Skill 的总注入预算为 3,000 字符。多标签任务去重后按稳定顺序轮流取完整规则，避免第一个长任务独占预算。预算不足时跳过整条并记录，不裁断规则。
- 明确这些是有条件的经验，不是每题必须执行的清单。已有证据已经满足 stop 时，不为完成 action 再查一次。
- Task 的具体条件与 Domain 的一般建议都必须服从当前题目的格式、真实工具能力和直接观察。冲突时不能无条件选择更长或更细的检查流程。

首轮不新增 Skill 检索器或模型路由。Task 选择由已有标签完成，when 条件由 Agent 在已有决策中判断。只有验证表明这种简化仍不足，才考虑额外路由机制。

### 7.2 Memory 先来源过滤，再相关性排序

自动检索仍每题开始一次，继续复用现有 Memory 配置，不恢复手动工具：

```text
明确的当前来源与查询时间
  → 来源及可用时间过滤
  → 当前问题的语义 Query
  → 相似度阈值 + Top K 上限
  → 完整条目预算
  → 紧凑注入，可为空
```

首轮来源规则：

- LVBench 只接受相同 video_id 的事实。适配器设置明确的 memory_context。
- MedVidBench 只接受相同帧序列坐标来源的事实。即使原视频相同，帧序列不同也不直接复用局部时间。
- EgoLife 只接受相同主体且 source.query_time 不晚于当前 query_time 的事实。保留先过滤未来来源再取 Top K 的规则，并检查定位所需的时间坐标。
- 当前来源未知或无法比较，返回空，不退化为全库检索。
- 来源身份使用稳定的数据集与视频/帧标识，不能因训练与评测机器的绝对路径不同而改变。MedVidBench 仍要求完整帧序列和 FPS 一致，不能仅用相同视频名放宽范围。
- 来源过滤后无候选，直接返回空，跳过 Query Embedding。空结果不添加 Memory 标题、提示说明或占位文本，Agent 输入保持与关闭 Memory 时一致。

Query 由各适配器已有的题目字段确定性构造，去掉输出格式、角色说明、视频总时长等固定模板，保留实际问题、必要实体、动作和时间约束。来源、query_time 通过结构化参数传递，不从自由文本猜测。LVBench 已有问题中的选项等有用信息不随意删除。MedVidBench 不盲目按句号裁剪长题，保留动作及程序上下文。

Top K 是上限，不是必须填满。首轮沿用 K=3、相似度阈值 0.5，以隔离来源过滤的效果，不同时搜索多个阈值。EgoLife 同人物但不同事件的误召回仍需在训练验证集分析，不能以人物相同宣称问题已经解决。相似度阈值的后续标定只用验证集，不按本次测试答案调参。

### 7.3 将 Memory 用作局部事实或检查入口

注入每条记忆的简短事实、稳定来源 ID、事件位置、可用时间和实际不确定性，必要时附一小段引用。完整路径、整段 context、长事件重复描述和全部引用留在产物里。首轮所有 Memory 注入文本合计不超过 1,600 字符，按排名保留完整条目，过长条目跳过并记录。

- 同来源事实可以帮助缩小候选区间，优先检查相关位置，不必重复从全视频 overview 开始。
- 当前观察与记忆冲突时，明确处理冲突，不能让历史状态覆盖当前证据。
- Memory 中某次状态不能直接回答新的“最后一次”或习惯问题，必须尊重问题的时间范围。
- 继续保留当前最低视觉证据要求。首轮主要验证减少无效搜索，不因检索命中就开放零视觉调用。将来若允许可信历史事实直接回答，应单独实验，不能把所有高相似度记忆自动当作可信证据。

Skill 与 Memory 组合时，Skill 负责选择检查与停止策略，Memory 提供候选事实和位置。同一条记忆已经提供候选区间时，不再由 Skill 强制增加一次无目的全局扫描。仍由原 Agent 决策，不增加额外规划模型。

## 8. 最小代码落点与实施顺序

不调整目录结构，不修改第三方数据，不改历史输出，不给 `train_offline.sh` 增加版本分支或新一层配置。继续通过现有脚本训练并执行四组评测，重复实验使用新的运行目录。

| 优先级 | 文件 | 修改目的 |
|---|---|---|
| P0 | 现有 records / trajectories / reports 的分析流程 | 固定样本与统计口径，先复跑 Base 衡量波动；这是实验步骤，不增加训练阶段 |
| P1 | `videospy/evolving/reflector/model.py` | 在同次分类中区分结果与证据；Skill 输出短规则；Memory 返回引用 ID 和局部事实 |
| P1 | `videospy/evolving/reflector/evidence.py` | 原文片段 ID、回填引用、来源位置可追溯 |
| P1 | `videospy/evolving/reflector/runner.py` | 绑定确定性结果状态与成本，传入反思；沿用分组、并发和失败统计 |
| P1 | `videospy/evolving/optimizer/skill_optimizer.py` | 工作规则逐组更新、来源集合去重统计、结束时确定性筛选、Domain 跨任务依据；均放在现有文件，不新增统计 Agent |
| P1 | `videospy/evolving/storage/memory_store.py` | 保存最终规则 JSON 与依据统计；来源过滤在相似度/Top K 前，空候选不 Embedding；完善检索审计 |
| P1 | `videospy/evolved_config.py`、`videospy/agent.py` | 确定性渲染、预算、紧凑注入、无命中不改变输入 |
| P1 | `videospy/evolving/common/memory_scope.py`、三个 `benchmark/*/run.py` | 明确来源身份、语义 Query、query_time 与当前样本 ID |
| P1，EgoLife 专项 | `benchmark/egolife/timeline.py`、来源读取相关位置 | 事件与日历时间转换、映射身份与缺失处理 |
| 随上述改动 | `tests/test_offline_v19.py`、`tests/test_evolved_memory_injection.py` 及已有 benchmark 测试 | 补充协议、预算、来源过滤和真实字段结构回归测试 |

`memory_optimizer.py` 只在新时间元数据接入确有需要时修改，不重写去重。`pipeline.py` 只为新规则状态存取和摘要作必要连接，不重做运行保障。预算先作为少量明确常量落在现有负责模块，不引入通用配置框架；后续确实需要预算消融时再集中暴露。

建议按三个可独立评估的小步实施：

1. **Skill 改进**：分类的绝对结果信息、规则结构、逐组依据统计、最终筛选、长度预算和推理渲染一起落地，先测 Skill Only。用相同预算、相同分组比较按有效支持筛选与只保留最新规则的结果，检查统计是否带来额外价值。
2. **Memory 改进**：局部事实、引用回填、来源过滤、紧凑注入一起落地，先测 Memory Only。EgoLife 时间修复是解释时间类结果的前提，不能搁置后宣称相对时间收益。
3. **组合与复核**：原四组消融复跑，核对完整输入、命中范围与逐题变化，再判断是否需要第二轮调整。

不在一个实验里同时修改模型大小、基础 max_steps、视觉采样帧数、数据划分和所有检索阈值。旧来源仍可用于初步对比，但正式结论应记录其配置差异；需要更新来源时，三个实验版本共用同一份新来源，不让算法和数据同时变化。

## 9. 验证方案与通过标准

### 9.1 代码与产物检查

本轮通过本地测试检查以下程序不变量，真实内容质量和收益按 9.2 另行验证：

- 一个多标签轨迹只分类一次，z-score / threshold 边界及原分组行为正确。错误答案的相对 Good 不会成为正向决策示范。
- 全 Bad 组允许 null；组内失败保留此前工作状态，发布必须核对通过；规则 ID 只能引用有效来源，未修改规则不能自动获得本组全部来源。
- 同一轨迹重复出现、检查点复用、续跑或规则合并不会重复计数。仅改措辞保留依据，改变实际条件或决策不继承无关计数；发现矛盾后不能仅靠高频入选。
- 单条有效依据可以支持发布，全部引用被淘汰或标为 uncertain 时不发布。工作状态与最终结果各自满足容量和字符预算，续跑不会把最终压缩结果当作全部历史状态。
- Task、Domain 和总注入预算都生效，按完整规则取舍。JSON / SQLite / 续跑加载一致，Domain 最多一次，多标签任务不重复注入相同规则。
- 引用片段 ID 可以确定性回到原文，非法 ID 或失败工具不能入库。一次局部观察不能通过模板直接变成全局否定或最新事件的示例产物。
- Others 与分类失败仍可提取 Memory。合法 null、过滤为空、去重无新增仍是正常结果。
- LVBench 跨视频排除，MedVidBench 跨帧序列排除，EgoLife 未来来源排除后再 Top K。空候选不调用 Embedding，空检索的 Agent 初始输入与关闭 Memory 完全一致。
- EgoLife 时间映射覆盖跨日、录制间隙、边界、缺失映射和事件时间不同于来源 query_time。未知坐标不能生成日历事实。
- 单项失败 warning 后继续，成功检查点复用，修改协议不混用旧反思成果；原三个 train_offline.sh 仍可进入训练和四组评测。

这些测试能确认逻辑和接口，不能证明模型质量或稳定收益。语义规则与事实质量需要实际产物抽查，不能写一个检查关键词的测试就声称已解决。

### 9.2 研究验证安排

1. 从原训练清单中留出验证子集，固定后不随版本改变。LVBench / MedVidBench 按视频分开，用于 Skill 泛化验证；EgoLife 在训练范围内保留较晚查询用于验证，严格执行 Memory 可用时间约束。验证题不参与对应版本的反思。
2. 本次 V19 测试结果已用于问题发现，今后在同一测试集上的结果属于迭代验证。需要更独立的结论，应预先冻结新的验证/最终评估安排，不能继续按同一测试题的答案设计规则。
3. 先做相同配置的 Base 重复运行，确认零组件条件下的答案和成本波动。随后四组在相同题目、相同模型服务配置下至少重复 3 次，保存运行次序和 seed；交替执行组次以减少服务时段影响。3 次是最低观察量，小样本高方差时增加重复，不把它当显著性的保证。
4. LVBench / EgoLife 报告总体、任务、命中/未命中子集及配对的错变对/对变错。LVBench 多标签任务不是互斥分桶，不能简单相加。
5. MedVidBench 分别报告各官方任务指标、NAP_exact_acc 与相应成本。LLM 评分使用相同 Judge 配置并保留结果波动，不能混合不同尺度成一个人为综合分数。
6. 本轮保留原泛化划分，Memory 零注入明确标为未验证，不新增同源评测。未来研究事实复用时，另行设计共享视频、不同问题且有明确可用边界的评估轨道，单独报告，不能替换原跨视频结果或输入目标问题答案。

### 9.3 必须记录的最少诊断信息

复用现有 JSON/日志，不建立新监控系统：

- 每题实际 Task/Domain 规则 ID、注入字符数和预算跳过数。
- 每题 Memory 原始候选数、来源/未来时间过滤数、最终 ID 与相似度、来源关系、注入字符数、空结果原因。关联 sample_id，不只保存 query hash。
- 准确率或任务指标、Agent 轮数、实际视觉调用数、失败/重复调用数、达到步数上限比例、input/output/total tokens。Embedding 耗时和训练成本另列，不混作推理 Token。
- Memory 是否真的提供答案证据或缩小搜索范围，只在抽查或有明确引用时作判断。命中不等于被使用，更不等于产生收益。
- Skill 每条规则的成功支持、失败案例、矛盾反例、独立来源和首次出现组号，以及最终入选/未入选原因、重复/未变更新数。只因容量未入选不能标为低质量。Memory 保留成功/失败/null/去重数。产物越多不是越好。

三个 benchmark 的 `records.jsonl` 增加逐题 `evolution_usage`，`metrics.json` 和 `report.md` 汇总实际注入题数、条数、字符数、预算跳过、空记忆原因、来源排除、最大步骤与重复视觉调用数。MedVidBench 保留独立官方 `evaluation.json`，新增 metrics.json 的 task_metrics 沿用官方/原本诊断指标，不求跨任务综合分数。

缺少轨迹诊断时记为 unknown/missing，不能记为零命中。Memory 开启、诊断完整且全部零注入时注明：本次 Memory 未实际参与推理，不能据此判断 Memory 收益或与 Skill 的交互效果。诊断不完整则只说明尚不能确认。实际注入仅证明模型看到了内容，不证明它采纳了规则或获得收益。

### 9.4 如何判断值得保留

- 在验证集上优先排除明显退化。相同准确率下成本更低，或成本相近时准确率更高，都是可报告的收益。准确率提高但成本显著增加，必须作为权衡呈现，不算同时实现效率提升。
- 最终报告重复运行的均值、离散程度和配对差值；有需要时按视频分组计算置信区间。未命中组仍出现的大幅波动不能归功于 Memory。
- 组合组与 Base、两个单组件分别比较。只有观察到组合优于较好的单组件，才能讨论互补收益；更严格的超加性需要另行定义和检验。
- 按适用任务讨论一致趋势，不要求同一个视频事实在无关视频上强行发挥作用。不因某个 benchmark 没有 Memory 可用而调低阈值填满 Top K。
- 单元测试通过、checkpoint 成功、Skill 变短、Memory 入库率提高，都不是最终训练有效的替代证据。

### 10.22 决策案例路径与新授权（2026-09-12）

用户已明确同意 Memory 扩展为跨视频推理案例，以及小批量 qwen3.6-flash 校验。10.18 的三帧请求随后完成。外部模型识别出 1700 秒实际是棉花糖容器，拒绝旧候选，但仍把机器模板数量报告为 6。它不能作为细粒度视觉真值。结果保存在 `lvbench_review_external/grounded_reflection_probe.json`。

旧框架同时存在三类问题：同视频事实库不能迁移到 LVBench 跨视频测试；整条轨迹答对不证明中间动作有效；可追溯工具原文仍可能包含视觉错误。调整为先提取具体决策案例，再从案例归纳 Skill。分类只用于选择候选来源，案例还需单独检查动作是否解决原问题，不能直接继承正确性。

- 案例提取只输出过去子问题、结果概括和原工具消息编号。具体工具及参数由程序绑定、复制，避免模型编造当时采取的动作。完整原观察保存在引用中。
- 案例审查与 Skill 审查分开。具体案例不要求自身已经抽象成通用规则，Skill 的概括失败或容量限制不再阻止案例入库。审查只检查文字证据的推理支持，不声称重看视频核实了事实。
- Memory 用 `kind` 区分原观察与推理案例，同一来源可以各存一条。原观察继续限制在同视频，案例允许同一 benchmark 内跨视频，EgoLife 仍检查来源查询时间，不使用未来轨迹。历史坐标只属于案例，不能作为当前视频事实。
- 案例索引和检索去掉选项、输出要求与运行时查询时间，匹配问题类型；原观察仍可按具体实体检索。推理提示明确标注历史案例，并维持总字符预算。
- Skill 从具体案例的原动作与观察归纳条件、动作、停止标准，再按原证据复核。没有案例的组仍保留原轨迹归纳路径。

第一轮固定六例对照中，4B 经常抄错引用、超出分字段字数，或把源时间写成规则；qwen3.6-flash 也出现过场景化规则和错误证据归因。因此简化为程序绑定动作和编号引用，并把具体案例与抽象 Skill 分成两步。早期探针在 `decision_cases/` 与 `decision_cases_v2/`，其中原始成功输出不等于已认可的训练成果。

LVBench 新 debug 运行 `self_openai_Qwen3.5-4B_20260912_084056_e0428d8` 用于首次完整联通检查。它启动时尚未包含后续独立案例审查、程序复制动作和案例检索去选项三项改动，需与后续运行区分。该运行的模型审查保留一条用餐后位置变化规则，但场景条件仍窄，不能仅凭保留状态称为有效 Skill。后续效果与最新代码测试结果另行补记。

### 10.25 当前入口与结果判读

普通入口继续使用已有配置中的 Agent 模型，按顺序执行，不同时启动两个脚本：

```bash
MODE=debug WORKERS=1 bash experiments/train/lvbench/train_offline.sh
MODE=lite WORKERS=1 bash experiments/train/lvbench/train_offline.sh
MODE=debug WORKERS=1 bash experiments/train/egolife/train_offline.sh
MODE=lite WORKERS=1 bash experiments/train/egolife/train_offline.sh
```

Skill review 统一使用 `evolving.reflector.model`，与提取、生成共用模型客户端，不再单独配置审核模型。每个 Task 完成分组学习后，审核最终候选规则及引用证据，输出保留、删除或不确定的判断。审核使用独立请求和审核提示词，不直接沿用生成对话；格式错误仍允许一次纠正。

审核现在对保留的每条规则证据与推理案例分别输出 `action`、`scope`、`conclusion` 三项检查，全部为 true 才能保留。false 或不确定不能被笼统的 keep 覆盖。动作检查核对真实工具与参数，范围检查核对人物、时间及先后关系，结论检查区分具体观察与工具自己的推断。Task 审核同时接收完整轨迹的工具调用名称清单；对成功支持，规则动作中无条件要求但源轨迹从未调用的视觉工具由程序直接剔除该支持；包含备选、禁止或条件分支的动作交由语义审核判断，避免把仅被提及的工具误当成必需步骤。失败案例可以支持未实际执行的改进建议，但不能因此成为成功证据。该机制不重新验证视频，不自动改写候选，也未新增观察 Memory 的语义审核；它首先约束文字 Skill 与推理案例的成功声明。共享审核逻辑纳入 checkpoint 身份，旧审核结果不会直接复用。

debug 样本仅用于检查链路。可执行停止条件要求至少 8 条符合条件的训练轨迹及 2 个任务类别，debug 中缺少该规则可能是正常的样本不足。`skills.json` 中的 `execution` 表示程序执行规则，`validation` 保存训练回放对照，它不会作为文字追加到模型提示。Memory 的 `kind` 区分同源原观察与可跨视频迁移的推理案例。

2026-09-13 修正：停止控制与文字 Skill 独立学习，`selection.skill_strategy` 记为 `independent_stop_and_text`。停止规则通过回放后仍执行 Task 分组、生成和审核，有至少两个通过审核的 Task 时继续生成文字 Domain Skill。最终在现有容量限制内合并已通过回放的停止规则和文字规则；文字审核拒绝或失败不影响停止规则与 Memory 发布，停止规则未通过也不影响文字学习。下文实验中 `replay_validated_execution` 跳过文字生成的记录属于旧行为。各自审核或回放通过不代表组合有效，仍须通过后续 Base、Skill、Memory、Skill + Memory 对照检验；当前流程没有自动按评测收益选择发布版本。

效果应结合实际注入记录判读。规则或案例存在但未命中时，不能把成绩变化归因于它们。每组比较同一批问题，同时报告正确数、轮数、Token、工具错误和真实命中；组合组再与两种单独使用的组比较。文字审核通过、训练回放通过和单题收益，都不能替代这一步。

固定 12 题筛查四组已完成：Base 为 6/12、7.00 轮、49,331 Token；Task Skill 为 5/12、7.17 轮、44,048 Token；Memory 为 6/12、8.42 轮、57,826 Token；组合为 7/12、10.42 轮、67,871 Token。两种含 Memory 的组都在 6/12 题实际注入跨视频案例，同源原观察未命中。组合比 Base 多答对 1 题，但单独 Skill 退步，Memory 没有准确率收益，组合成本增加，尚未达到目标。

### 10.26 分离观察波动、执行规则和案例干扰
