## 20260814
以下是代码实际行为和设计描述之间的主要差异。

1. 字幕区间过滤条件有误

skim 和 focus 使用了：

subtitle.start <= end_time or subtitle.end >= start_time

正确的区间相交判断应当使用 and。当前写法通常会把大量不属于目标区间的字幕也带进去。

2. 工具约束主要依赖提示词

提示词要求：

- 每轮只调用一个工具
- skim 区间至少 16 秒
- focus 区间不超过 16 秒

Python 层没有强制校验。模型如果生成错误时间或多个工具调用，执行层仍可能接受。

3. focus 并不是真正的 1 FPS

代码按区间均匀采样最多 16 帧，没有以秒为单位生成固定 1 FPS 时间点，因此实现和工具描述不完全一致。

4. 配置来源不统一

Agent 的提示词使用传入的 self.config，但工具采样数量直接读取模块级 general_config。如果程序调用方动态修改配置，两处可能不一致。

5. YouTube 和自动字幕尚未接通

README 声称支持 YouTube URL，依赖中也包含 yt-dlp 和 Whisper，但当前 Agent 直接把 video_path 传给 VideoReader，代码里没有下载视频或自动转录逻辑。

6. 异常信息被吞掉

工具失败后轨迹里只保存 "Tool execution failed."，没有具体异常，调试会比较困难。

7. 空轨迹可能导致序列化异常

Trajectory.to_dict() 使用：

max(s.step_id for s in self.steps)

如果所有 Action 解析都失败，steps 为空，这里会再次报错。

8. 配置文件包含明文 API 密钥

config/general.yml:1 已被 Git 跟踪且包含明文密钥。建议立即废弃并轮换该密钥，改成只保存环境变量名称或占位符。

9. 提示词存在逻辑冲突

Final Answer Policy 中要求使用工具收集证据，但又写着调用其他工具后不要调用 answer。代码实际允许后续步骤调用 answer，所以这里更像是提示词表述错误。

这个 Agent 可以概括成：

> LLM 负责决定看哪里，Python 负责准确取帧，视觉 LLM 负责解释画面，轨迹负责保存证据，最后由 LLM 汇总答案。

它的优点是实现短小、模块边界清晰，overview → skim → focus 也很好地对应了人类观看长视频时“先浏览、再定位、后确认”的过程。当前薄弱点主要集中在运行时约束、配置安全、字幕过滤和异常处理上。

我完成了源码静态检查，Python 语法编译通过。仓库没有测试目录，当前环境又缺少 decord，所以 CLI 和真实视频推理没有实际运行。
